
# 育児支援 iOS アプリ 要件定義書 v0.1

**ステータス:** ドラフト / 未承認
**対象プラットフォーム:** iOS ネイティブ (iPhone 優先、iPad は v2 以降)
**想定リリース:** MVP を約 4〜6 ヶ月

---

## 0. この文書の読み方

本書は「作るもの」を確定させるための叩き台であり、**すべてを v1 で作らない前提**で書いている。
各機能に `[MVP]` / `[v1.1]` / `[v2]` / `[将来]` のフェーズラベルを付与した。
MVP に入っていない機能は「やらない」ではなく「今は決めない」の意味である。

## 1. 背景と課題

### 1.1 現状の問題

出産・育児に必要な情報は、性質ごとに完全に分断されている。

| 情報の種類 | 現在の所在 | 問題 |
|---|---|---|
| 日々の記録 | 記録アプリ、紙 | 記録できるが、その先の判断につながらない |
| 発育の評価 | 母子健康手帳 | 手書き。過去との比較や共有がしにくい |
| 制度・給付金 | 自治体サイト、PDF | 1,741 自治体でバラバラ。存在自体を知らない |
| 申請期限 | どこにもまとまっていない | 1 日過ぎると受給権が消えるものがある |
| 夜間・救急の判断 | #8000、Web 検索 | 焦っている状況で探せない |
| 受診可能な医療機関 | 各医療機関サイト | 診療時間しか載っておらず実態と乖離 |

親は「何を知らないかを知らない」状態に置かれている。とくに制度は、**知らなければ損失が確定する**にもかかわらず、能動的に調べた人だけが受け取れる構造になっている。

### 1.2 本アプリが解こうとする課題

1. **取り逃し防止** — 期限のある手続きを、期限前に、当人の条件に合わせて通知する
2. **判断支援** — 記録・症状・月齢から「今どうすべきか」の一次判断を助ける
3. **情報の非対称の解消** — 世帯内(とくにパートナー)で情報とタスクを同期させる

### 1.3 やらないこと (非スコープ)

- 医学的診断・治療方針の提示
- 医療機関の予約代行、受診勧奨の断定的表現
- SNS・掲示板などのユーザー間コミュニティ (v1 では運営コストが見合わない)
- EC・物販
- 妊娠中の詳細な妊婦健診管理 (v1.1 以降で検討)

## 2. ターゲットユーザー

### 2.1 プライマリ

**第一子の妊娠後期〜生後 18 ヶ月の保護者**
制度も育児も初めてで、情報探索コストが最大化している層。生活が一変し、新しいアプリを入れる動機が最も強いタイミング。

### 2.2 セカンダリ

**同居パートナー**
主たる記録者ではないが、通知の受け手・タスクの実行者になる。多くの家庭で情報格差の当事者。

### 2.3 検討すべきニッチ (差別化の観点)

以下は市場が小さい代わりに代替サービスが事実上存在せず、口コミが極端に強く効く。v1 のターゲットとして「あえて狭く取る」戦略も成立する。

- 多胎児世帯 (成長曲線・予防接種・制度がすべて条件違い)
- NICU 卒業児 / 早産児 (修正月齢での評価が必須だが対応アプリが少ない)
- ひとり親世帯 (制度が別体系)

> **意思決定が必要:** 「全員向けの 2 番手」を狙うか「特定層にとっての唯一」を狙うか。本書は前者を前提に書いているが、後者を選ぶ場合は §4.3 の発育曲線と §4.5 の制度エンジンの要件が大きく変わる。

## 3. プロダクト原則

要件が競合したときの判断基準。上にあるものが優先する。

1. **間違えないこと > 便利であること**
   金額・期限・医療情報は、不確かなら出さない。すべての情報に出典と取得日を持たせる。
2. **片手・暗所・0.5 秒**
   主要操作は授乳中の片手操作を前提に設計する。記録に 3 タップ以上かかる設計は却下。
3. **不安を煽らない**
   平均との比較は、逸脱の指摘ではなく文脈の提供として設計する。
4. **通知は資産、乱発は負債**
   通知は「行動が必要なとき」だけ。読み物のプッシュは行わない。
5. **オフラインで動く**
   記録と緊急時ガイドは、電波がなくても機能する。

## 4. 機能要件

### F-1. オンボーディング / 世帯プロファイル `[MVP]`

制度判定と発育評価の精度は、ここで取得する属性で決まる。ただし初回に全部聞くと離脱するため、**段階的に聞く**設計とする。

**初回に必須で取得する項目**

| 項目 | 用途 | 必須 |
|---|---|---|
| 子の生年月日 (または出産予定日) | 月齢計算の基準 | ○ |
| 在胎週数 | 修正月齢の算出 | ○ |
| 出生時体重 | 低出生体重児の判定 | ○ |
| 居住自治体 (市区町村コード) | 制度判定の主キー | ○ |
| 子の性別 | 発育曲線の選択 | ○ |

**後から追加で取得する項目 (プログレッシブ・プロファイリング)**

- 世帯構成 (ひとり親 / 二親)、第何子か、多胎か
- 就業状況・雇用保険加入状況 (育児休業給付の判定)
- 加入医療保険の種別 (国保 / 被用者保険)
- 世帯所得帯 (レンジ選択。実額は取らない)

> **要件:** 所得は「判定に必要な最小の粒度」でのみ取得する。実額を保持しない設計とし、閾値をまたぐレンジのみを保存する。

**受け入れ基準**
- 初回オンボーディングは 60 秒以内、5 画面以内で完了する
- 未入力項目がある場合、制度一覧に「判定に情報が足りません」と表示し、その場で補完できる

### F-2. 日々の記録 `[MVP]`

**記録対象**

| カテゴリ | 項目 | 優先度 |
|---|---|---|
| 授乳 | 母乳 (左右・時間) / ミルク (量) / 混合 | MVP |
| 排泄 | おしっこ / うんち (性状) | MVP |
| 睡眠 | 開始・終了 | MVP |
| 体温 | 実測値 | MVP |
| 身体計測 | 身長・体重・頭囲 | MVP |
| 投薬 | 薬剤名・時刻 | v1.1 |
| 離乳食 | 食材・反応・アレルギー疑い | v1.1 |
| 搾乳 | 量・時刻 | v1.1 |

**必須要件**

- **ワンタップ記録**: ホーム画面から 1 タップで記録開始できること。授乳は開始/停止のトグル。
- **完全オフライン動作**: ネットワークなしで記録・閲覧できること。同期は後追い。
- **事後編集**: 記録忘れに対応し、時刻を遡って追加・修正できること。
- **アレルギー記録の分離**: 離乳食の記録は、後から「初めて食べた日」を一覧で引ける構造にすること (アレルギー発症時に医師に見せる用途)。

**受け入れ基準**
- 授乳記録の開始は、アプリ起動から 2 タップ以内
- 機内モードで 7 日間記録し、復帰後にすべて同期されること
- 同一レコードを 2 端末から同時編集した場合、データが消失しないこと (§8.3 参照)

### F-3. 発育の評価と比較 `[MVP]`

#### 4.3.1 データソース

母子健康手帳に掲載される乳幼児身体発育曲線は、こども家庭庁 (旧厚生労働省) が概ね 10 年周期で実施する **乳幼児身体発育調査**の結果に基づく。直近の調査は令和 5 年 (2023 年) 9 月に実施されており、結果は母子健康手帳の発育曲線に反映される。

> **実装前に確認が必要:** 令和 5 年調査に基づく発育値が公表・適用済みか、平成 22 年調査の値が現行かを確認し、**母子健康手帳と同一の値**を採用すること。手帳と違う曲線を出すと、それだけで信頼を失う。

**採用する指標**

- 身長・体重・頭囲のパーセンタイル曲線 (3〜97 パーセンタイル)
- 幼児の身長体重曲線 (肥満度判定用) — v1.1
- カウプ指数は表示しない (誤解を招きやすいため)

#### 4.3.2 修正月齢

在胎 37 週未満で出生した場合、**修正月齢での評価をデフォルトとする**。
暦月齢との切り替えを可能とし、どちらで見ているかを画面上に常時明示する。

#### 4.3.3 表示要件 (安全性に直結)

| やること | やらないこと |
|---|---|
| 帯の中に自分の子の点を置く | 「平均より小さい」等の評価語を出す |
| 前回計測からの変化の向きを示す | 偏差値・順位・スコア化 |
| 曲線からの逸脱が続く場合のみ「健診で相談する項目に追加」を提案 | 「異常」「要注意」等のアラート表現 |
| 3〜97 パーセンタイルの帯全体が正常範囲であることを併記 | 単発の計測値に対する判断の提示 |

> **設計判断:** 平均との比較は不安を増幅させる副作用がある。**逸脱の指摘ではなく、健診での相談ネタの生成**として機能させる。これが本機能の存在理由。

### F-4. スケジュール管理 `[MVP]`

#### 4.4.1 予防接種スケジューラ

- 定期接種・任意接種の標準スケジュールを月齢から自動生成
- 接種間隔ルール (同時接種可否、中 27 日以上等) を制約として保持
- 接種済み記録の入力により、以降のスケジュールを再計算
- 遅延した場合のキャッチアップスケジュールを再構成

> **要件:** 予防接種スケジュールは自治体・年度により変更される。定期接種の対象・回数はマスタデータとしてサーバ側で管理し、アプリ更新なしに差し替えられること。

#### 4.4.2 乳幼児健診

- 自治体ごとの健診時期 (3-4 ヶ月、1 歳 6 ヶ月、3 歳等) を反映
- 健診前に「相談したいことリスト」を自動生成 (F-2/F-3 の記録から候補を抽出)

#### 4.4.3 手続き期限カレンダー `[MVP・最重要]`

**本アプリの中核機能。** 期限を過ぎると受給権が失われる手続きを、世帯条件に応じて時系列に並べる。

対象となる手続きの例 (実装時に最新の制度で再確認すること):

- 出生届
- 児童手当の認定請求 (請求が遅れた月分は遡って支給されない扱いがあるため、遅延の金銭的損失が明確)
- 健康保険の加入手続き
- 乳幼児医療費助成の申請
- 育児休業給付・出生後休業支援給付等の各種申請
- 保育所の入所申込 (4 月入園は前年秋が締切)
- 未熟児養育医療給付 (該当世帯のみ)

**要件**

- 各手続きに「起算日」「期限」「所要書類」「窓口」「オンライン可否」を持たせる
- 期限の N 日前に通知 (N は手続きの重要度と準備所要時間から個別設定)
- 完了/対象外のマークができ、完了済みは非表示になる
- **すべての項目に出典 URL と情報取得日を表示する**

**KPI 案:** 「このアプリ経由で申請完了した手続き件数」「取り逃しゼロ達成率」

### F-5. 制度・給付金エンジン `[MVP (段階導入)]`

#### 4.5.1 データ取得方針

情報源は 3 層構造とする。**スクレイピングは最後の手段**であり、公式データを土台にする。

**第 1 層: 公式 API**

デジタル庁の**子育て支援制度レジストリ**は、自治体および国がデータベースに登録した子育て支援制度情報を取得できる API として、2025 年 9 月に概要が公開され利用申請の受付が始まっている。API は「外部連携制度・手続一覧検索 API」と「外部連携制度・手続詳細検索 API」の 2 本で、仕様書はマイナポータル API 仕様公開サイトの電子申請等 API 仕様書に含まれる。

> **アクション:** 開発着手と同時に API 利用申請を出す。承認待ちがクリティカルパスになる可能性が高い。

**第 2 層: オープンデータ**

自治体標準オープンデータセットでは、支援制度 (給付金) 情報について他のデータセットとフォーマットが大きく異なるため専用の項目定義書が用意されており、利用者の属性情報と紐づけたプッシュ型の案内が想定されている。本アプリの設計思想と一致する。

**第 3 層: クロール + 構造化抽出**

レジストリ未登録の自治体独自制度 (出産祝い金、紙おむつ券、多子世帯加算など) は、自治体サイトの HTML/PDF にしか存在しない。ここは差分埋めとしてクロールする。

法務面: 政府標準利用規約 (第 2.0 版) では、公開情報を複製・公衆送信・翻案等自由に利用でき商用利用も可能で、この規約は CC BY と互換性がある。また数値データや簡単な表・グラフは著作権の対象外とされ、この利用ルールの適用外となる。同規約は令和 6 年 7 月 5 日に「公共データ利用規約 (第 1.0 版)」として改訂され、地方公共団体でも適用可能であることが明記された。

> **クロール実施上の必須ルール**
> - 1 リクエスト/秒 以下、深夜帯優先
> - User-Agent に運営者名と連絡先 URL を明記
> - robots.txt を遵守
> - 出典の記載を必ず行う
>
> 著作権よりも**アクセス負荷による業務妨害の扱い**のほうが実務上のリスクが大きい (岡崎市立中央図書館事件の前例)。ここのコストは削らない。

#### 4.5.2 抽出パイプライン

```
公式API/オープンデータ ─┐
                        ├→ 正規化 → スキーマ検証 → 人手レビュー → 本番DB
自治体サイトクロール ───┘         (金額・期限は必須レビュー)
        │
        └→ HTML/PDF → LLM構造化抽出 → 信頼度スコア付与
```

**スキーマ必須項目**

| フィールド | 説明 |
|---|---|
| `municipality_code` | 全国地方公共団体コード |
| `program_name` | 制度名 |
| `eligibility` | 判定ルール (機械可読な条件式) |
| `amount` | 金額 (定額 / 計算式 / 現物給付) |
| `deadline_rule` | 起算日と期限の定義 |
| `application_channel` | 窓口 / 郵送 / オンライン |
| `source_url` | 出典 URL **(必須)** |
| `fetched_at` | 取得日時 **(必須)** |
| `extraction_method` | api / opendata / llm_extract / manual |
| `confidence` | 信頼度 |
| `reviewed_by` | 人手レビュー者 (金額を含む場合は必須) |

#### 4.5.3 更新検知

- ソースページのハッシュ差分を日次で監視し、変更があったレコードのみ再抽出
- 年度替わり (4 月) と制度改正のタイミングで全件棚卸し

#### 4.5.4 UI 上の必須要件

- 制度カードには**必ず出典リンクと「◯年◯月◯日時点」を表示**する
- 判定に必要な属性が未入力の場合、「該当しない」ではなく「判定できない」と表示する
- 「この情報が古い / 間違っている」の報告導線を全カードに置く

> **展開戦略:** 全国 1,741 自治体を初期から埋めるのは不可能。**MVP は 1 自治体または 1 都道府県に限定**し、そこで精度を作り込む。カバレッジではなく正確性で評価される機能である。

### F-6. 医療機関検索・緊急時対応 `[MVP]`

#### 4.6.1 緊急時ガイド (オフライン必須)

夜間に発熱した、けいれんした、誤飲した — この瞬間にアプリが起動して圏外だったら価値はゼロ。**全文をアプリにバンドルし、オフラインで動作させる。**

- 症状別のトリアージ質問 (月齢 × 症状 × 随伴症状)
- 到達点は 3 つに限定: 「救急要請」「今すぐ受診」「様子見 + 再評価の目安」
- 公的相談窓口への直接発信 (#8000 小児救急電話相談、#7119、119)
- 誤飲時の中毒 110 番

> **安全性要件:** トリアージ結果は診断ではない。すべての分岐で「判断に迷う場合は #8000 または 119」への導線を残す。ロジックは小児科医の監修を必須とする。

#### 4.6.2 医療機関検索

厚生労働省の医療情報ネットのデータは、e-Gov のデータカタログで CC BY ライセンスのオープンデータとして提供されている。これを基盤とする。

> **既知の課題:** 医療機関データには表記ゆれが多い。医療機関コードの区切り文字の違い、法人名の省略形の有無、住所の都道府県表記の有無、診療科目に至っては 1,600 種以上の表記の違いが研究で報告されている。**正規化に相当な工数を見積もること。**

**機能**

- 現在地からの小児科 / 小児救急 / 夜間休日診療所の検索
- 「今開いている可能性が高い」の表示 (公表診療時間ベース。実態との乖離を明示)
- 予防接種実施医療機関のフィルタ
- 病児保育施設の一覧 `[v1.1]`

> **やらない判断:** 「今の待ち時間」「リアルタイム受け入れ可否」は魅力的だが、医療機関側にデータを出すインセンティブがなく、外れた場合の責任が重い。v1 では実装しない。ユーザー投稿型は密度が出るまで無価値なため、地域を絞った上で v2 以降に検討する。

### F-7. 知識アシスタント (RAG) `[MVP (機能限定)]`

#### 4.7.1 設計上の前提

**汎用チャットボットにしてはいけない。** 育児知識を答えるだけなら汎用 LLM で足りる。差別化は「モデル」ではなく「参照するデータ」にしかない。

したがって本アプリの RAG は、以下に限定した**回答範囲の狭い検索型アシスタント**とする。

**回答してよい領域**

1. 本アプリが保持する制度・給付金データ (F-5)
2. 監修済みの育児・health literacy コンテンツ
3. ユーザー自身の記録 (F-2/F-3) — 「先週より睡眠時間が短い」等の事実提示

**回答してはいけない領域**

- 診断、治療方針、薬剤の使用可否
- 医学的な予後の予測
- 保持データに根拠がない一般論

#### 4.7.2 アーキテクチャ

```
ユーザー質問
  → 意図分類 (制度 / 育児知識 / 自分の記録 / 医療判断)
      ├ 医療判断 → RAG を通さず F-6 のトリアージへ強制ルーティング
      └ その他 → ハイブリッド検索 (BM25 + ベクトル)
                  → 世帯プロファイルでフィルタ (自治体・月齢)
                  → リランク
                  → 生成 (根拠チャンクのみを文脈とする)
                  → 出典必須の検証ゲート
```

**必須要件**

- **根拠がない場合は答えない。** 「わかりません」と、代わりに調べるべき場所を返す。
- 回答には必ず出典と取得日を付す。
- 生成結果が医療的判断を含むかを判定するガードレールを、生成後にも通す。
- 質問と回答のログを収集し、答えられなかった質問をコンテンツ拡充のバックログに直結させる。

#### 4.7.3 評価

リリース前に、想定質問 300 件程度の評価セットを構築し以下を測定する。

| 指標 | 目標 |
|---|---|
| 出典付与率 | 100% |
| 事実誤り率 (金額・期限) | 0% (1 件でもあればリリース不可) |
| 医療判断への越境率 | 0% |
| 「わかりません」率 | 30% 以下 |

### F-8. パートナー共有 `[MVP]`

既存の育児アプリは「記録の共有」はできても「知識とタスクの共有」ができていない。ここが体験上の差別化点になる。

- 招待コードによる世帯への参加
- 記録のリアルタイム同期
- **手続きタスクの割り当て** (「児童手当の申請 → パートナー担当」)
- 相手が担当しているタスクの進捗が見える
- 通知の宛先を、担当者に応じて出し分ける

> **設計意図:** 「片方だけが全部把握している」状態を崩すことが目的。単なるデータ共有ではなく、**タスクの所有者が明示される**ことが要件。

---

### F-9. 通知 `[MVP]`

**原則:** 行動が必要なときだけ送る。読み物のプッシュは送らない。

| 通知種別 | タイミング | 優先度 |
|---|---|---|
| 手続き期限 | 期限の N 日前 (手続きごとに設定) | 高 |
| 予防接種 | 接種可能日の 3 日前 / 遅延時 | 高 |
| 健診 | 対象期間の開始時 | 中 |
| 記録リマインド | ユーザーが明示的に設定した場合のみ | 低 |

**要件**
- 種別ごとに ON/OFF 可能
- 夜間 (22:00〜7:00) は高優先度以外を送らない
- Notification Service Extension で内容をローカル復号 (§9.2)

### F-10. データポータビリティ `[v1.1]`

- 記録の CSV / PDF エクスポート
- 健診用のサマリー PDF 生成 (医師に見せる用途)
- 他アプリ (ぴよログ等) からのインポート
- アカウント削除時の完全消去

## 6. セキュリティ・プライバシー要件

### 6.1 法的位置づけ

本アプリが扱うデータは、個人情報保護法上の**要配慮個人情報**(健康情報)を含む。したがって:

- 取得時に利用目的を明示し、**明示的な同意**を取得する
- 第三者提供は原則行わない。行う場合は個別同意を取る
- 統計利用する場合も、匿名加工の要件を満たす処理を行う

### 6.2 実装要件

- 保存時暗号化 (端末: Data Protection Class A/B、サーバ: 保存時暗号化)
- 通信は TLS 1.3、証明書ピンニング
- 認証は Sign in with Apple を第一選択 (メールアドレスを持たない選択肢を提供)
- **子の氏名・写真をサーバに送らない設計を第一候補として検討する** (端末内保持 + E2E 同期)
- 分析ツールに健康データを送らない。イベント設計時に厳格なホワイトリスト方式を採る
- アカウント削除で全データを 30 日以内に物理削除

### 6.3 App Store 審査上の注意

- 医療系アプリとして審査される可能性が高く、医学的主張の根拠提示を求められる
- 緊急時ガイドは「医療行為の代替ではない」旨を明示する
- 監修者 (小児科医) の氏名・所属を明記する

## 7. 安全性要件 (最重要)

本アプリは、間違えると人が困る領域を 2 つ扱う。**金額**と**医療**である。

### 7.1 医療情報

| ルール | 実装 |
|---|---|
| 診断しない | 症状入力から病名を出力しない |
| 受診を止めない | すべての分岐に「迷ったら相談」の導線を残す |
| 監修を通す | トリアージロジックと健康コンテンツは小児科医監修必須 |
| 更新履歴を残す | コンテンツごとに監修日と監修者を保持 |
| 免責を出す | ただしバナーの連発はしない。重要な分岐点でのみ表示 |

### 7.2 制度・金額情報

| ルール | 実装 |
|---|---|
| 出典なしの情報を出さない | `source_url` を NOT NULL 制約とする |
| 断定しない | 「受給できます」ではなく「対象の可能性があります。窓口で確認してください」 |
| 人手レビュー | 金額を含むレコードは `reviewed_by` 必須 |
| 誤り報告を受ける | 全カードに報告導線 |
| 責任分界を明示する | 利用規約で最終確認責任がユーザーにあることを明記 |

> **設計上の要:** 「LLM が抽出したまま出す」構成にすると必ず事故が起きる。出典に飛べる設計にしておけば、誤りがあってもユーザーが自力で確認でき、責任分界も引ける。

## 8. データ設計

### 8.1 主要エンティティ

```
Household (世帯)
 ├ municipality_code, household_type, income_bracket
 ├─ Member (保護者) *
 │   └ role, notification_preference
 └─ Child (子) *
     ├ birth_date, gestational_weeks, birth_weight, sex, is_multiple
     ├─ CareLog (記録) *        … feeding / sleep / diaper / temperature / medication
     ├─ Measurement (計測) *    … height / weight / head_circumference
     ├─ Vaccination (接種) *
     └─ Checkup (健診) *

ProgramMaster (制度マスタ)      … サーバ管理・全ユーザー共通
 ├ municipality_code, eligibility_rule, amount, deadline_rule
 └ source_url, fetched_at, extraction_method, confidence, reviewed_by

TaskInstance (手続きタスク)      … Household × ProgramMaster の展開結果
 ├ due_date, status, assignee_member_id
 └ generated_at
```

### 8.2 マスタとユーザーデータの分離

- **ProgramMaster / GrowthReference / VaccineSchedule** はサーバ管理。アプリ更新なしで差し替え可能とする。
- **ユーザーデータ**は端末優先。同期はバックグラウンド。

### 8.3 同期・競合解決

- 記録は追記型 (append-only) を基本とし、更新より新規レコードを優先する設計にする
- 競合時は Last-Write-Wins ではなく、**両方保持してユーザーに提示**する (記録の消失は信頼を失う)
- 同期は CloudKit または独自バックエンド (§9.1 で判断)

## 9. 技術構成 (案)

### 9.1 選択肢

| レイヤ | 第一候補 | 代替 | 判断軸 |
|---|---|---|---|
| UI | SwiftUI | UIKit 併用 | チャート表現の自由度 |
| ローカル永続化 | SwiftData | Core Data | iOS 17 以降に絞れるか |
| 同期 | CloudKit | 独自 API + Postgres | 世帯共有の実装しやすさ / 将来の Android 展開 |
| バックエンド | — | Postgres + pgvector | 制度データと RAG インデックスを同居させられる |
| RAG | サーバ側 | — | インデックス更新の頻度が高いためサーバ必須 |
| チャート | Swift Charts | 自前描画 | パーセンタイル帯の表現力 |

> **重要な分岐点:** CloudKit は世帯共有 (CKShare) が楽で運用コストが低い一方、**Android 展開の道を塞ぐ**。育児アプリはパートナーの端末が Android である確率が相当高いため、独自バックエンドを推奨する。

### 9.2 通知の暗号化

制度通知は内容自体が世帯情報を含む。プッシュペイロードには識別子のみを載せ、Notification Service Extension で端末側から本文を取得・復号する。

## 10. UI 設計方針

> 詳細は §11 の画面一覧を参照。ここでは全体の設計思想を定義する。

### 10.1 中核となる制約

**このアプリの主要利用シーンは、片手・暗所・睡眠不足・泣いている赤ん坊の横、である。**

一般的なアプリの UX 原則がそのまま通用しない。以下を絶対制約とする。

1. **片手到達域**: 主要アクションはすべて画面下 1/3 に配置する。上部にプライマリ CTA を置かない。
2. **タップ数**: 最頻出操作 (授乳記録) は 2 タップ以内。
3. **文字量**: ホーム画面の情報量を絞る。読ませない。
4. **ダークモード優先設計**: ライトモードの流用ではなく、夜間表示を基準に設計する。
5. **誤タップ耐性**: 破壊的操作 (記録削除) は取り消し可能にする。確認ダイアログではなく Undo で解決する。

### 10.2 情報アーキテクチャ

タブは 4 つまで。5 つ以上にすると片手で押し分けられない。

```
┌─────────────────────────────────────┐
│  ①今日   ②成長   ③やること   ④きく  │
└─────────────────────────────────────┘
```

| タブ | 役割 | 中身 |
|---|---|---|
| **① 今日** | 記録のホーム | ワンタップ記録、直近のログ、次の授乳の目安 |
| **② 成長** | 蓄積の可視化 | 発育曲線、睡眠パターン、月齢別のマイルストーン |
| **③ やること** | 期限管理 | 手続きタスク、予防接種、健診。**バッジはここだけ** |
| **④ きく** | 知識アクセス | RAG、緊急時ガイド、医療機関検索 |

**緊急時ガイドの扱い:** ④の中に埋めるだけでは、焦っている状況で到達できない。以下を併用する。

- ホーム画面のヘッダに常時「緊急時」ボタンを固定表示
- ホーム画面クイックアクション (長押しメニュー) に登録
- コントロールセンターのウィジェット (iOS 18 以降)

### 10.3 タブ別の設計

#### ① 今日

```
┌───────────────────────────┐
│  さくら  生後 4ヶ月12日   [緊急時] │
│                                   │
│  最後の授乳から 2時間15分         │
│                                   │
│  ┌─────────┐  ┌─────────┐        │
│  │  授乳    │  │  ミルク  │        │  ← 大きなタップ領域
│  └─────────┘  └─────────┘        │     (最低 88pt 角)
│  ┌─────────┐  ┌─────────┐        │
│  │  睡眠    │  │  おむつ  │        │
│  └─────────┘  └─────────┘        │
│                                   │
│  ─ 今日の記録 ─────────────       │
│  14:20  授乳 左 12分              │
│  13:05  おむつ                    │
└───────────────────────────┘
```

- 「最後の授乳から◯時間」を最も大きく表示する。これが親が最も頻繁に確認する情報。
- 記録ボタンは 2×2 グリッド。片手の親指で 4 つすべてに届く配置。
- 授乳は「開始」でタイマーが走り、もう一度押すと停止。左右の切り替えはタイマー中に表示。

#### ② 成長

- 発育曲線は**帯の中の点**として表示する。線を引いて他人と比較させない。
- 帯全体が正常範囲であることを、グラフ内に常時テキストで書く。
- 修正月齢/暦月齢のトグルを目立つ位置に。
- スクロールで「今月のマイルストーン」(首すわり、寝返り等) に接続。ここは**達成度チェックではなく目安の提示**として書く。

> **注意:** マイルストーンをチェックリスト化すると、達成していない親を追い詰める。「まだの場合も個人差の範囲です」を各項目に添えるか、そもそもチェックボックスにしない。

#### ③ やること

- 時系列の縦タイムライン。上が直近。
- カードは 3 種類のみ: **期限あり (赤系アクセント) / 予定 (通常) / 完了 (グレーアウト)**
- 各カードに担当者アイコン。未割当は「担当を決める」CTA。
- カードを開くと: 何のための手続きか → 必要書類 → 窓口 → 出典リンク → 「◯年◯月時点」

#### ④ きく

- 検索窓ではなく、**よくある質問のチップを先に見せる**。空の入力欄は何を聞けるか分からず離脱を生む。
- 月齢に応じてチップの内容を変える (生後 1 ヶ月なら「授乳間隔」「黄疸」、8 ヶ月なら「離乳食」「人見知り」)。
- 回答は必ず出典カード付き。
- 医療的な質問を検知したら、回答せず緊急時トリアージに遷移する。

### 10.4 緊急時ガイドの UI

**通常の UI 原則をすべて捨てる。**

- 装飾ゼロ。フォントサイズ最大。1 画面 1 問。
- 選択肢は 2〜3 個まで。スクロール不要。
- 背景は高コントラスト。夜間に画面が明るすぎないよう配慮しつつ可読性を優先。
- 結論画面では、行動 (電話をかける) が最大の要素になる。

```
┌───────────────────────────┐
│                                   │
│   ぐったりして、                  │
│   반応が鈍いですか？              │
│                                   │
│   ┌───────────────┐   │
│   │      はい             │   │
│   └───────────────┘   │
│   ┌───────────────┐   │
│   │      いいえ           │   │
│   └───────────────┘   │
│                                   │
│   判断に迷う → #8000 に電話       │
└───────────────────────────┘
```

### 10.5 トーン&マナー

- **評価語を使わない。** 「良い / 悪い」「順調 / 遅れ」を避ける。
- **励まさない。** 過剰なポジティブ表現 (「今日もお疲れさま!」の乱発) は、しんどい時に逆効果になる。
- **記録の欠損を責めない。** 「3 日間記録がありません」は表示しない。ストリーク機能は入れない。
- 色は低彩度を基本とし、警告色は緊急時と期限にのみ使う。

## 12. リリース計画

### Phase 0 — 検証 (着手前 2〜4 週)

- 子育て支援制度レジストリ API の利用申請を提出
- 対象自治体を 1 つ決め、制度データを**手作業で全件収集**してみる
  → ここで「API で何割埋まり、何割が手作業か」が判明する。これが事業の成否を決める
- 小児科医の監修者を確保する
- 発育曲線の参照値 (令和 5 年調査の適用状況) を確定する

### Phase 1 — MVP (約 4〜6 ヶ月)

F-1 / F-2 / F-3 / F-4 / F-6 (緊急時ガイド) / F-8 / F-9
制度エンジン (F-5) は**対象自治体 1 つに限定**して搭載。
RAG (F-7) は制度データのみを対象とした限定版。

**リリース判定基準**
- 制度データの金額・期限の誤り 0 件 (全件人手レビュー済み)
- 緊急時ガイドの監修完了
- 発育曲線が母子健康手帳と一致
- 機内モードで全記録機能が動作

### Phase 2 — v1.1 (+3 ヶ月)

対象自治体を都道府県単位に拡大 / 医療機関検索 / 離乳食・投薬記録 / エクスポート

### Phase 3 — v2

多胎・早産児対応の深化 / 病児保育 / 保活支援 / Android

## 14. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| 制度データの誤りによる金銭的損害 | 致命的 | 全件出典必須、金額は人手レビュー、免責を規約に明記 |
| 緊急時ガイドの判断ミス | 致命的 | 医師監修、迷ったら受診に倒す設計、断定表現の禁止 |
| レジストリ API のカバレッジ不足 | 高 | Phase 0 で実測。不足するならクロール比率を上げるか対象自治体を絞る |
| 制度データの運用コスト | 高 | 更新検知の自動化。それでも人手は必須と割り切って予算化する |
| 医療機関データの正規化コスト | 中 | 表記ゆれ対応を工数に織り込む。v1 は診療科目の粒度を粗くする |
| 既存アプリとの機能重複 | 中 | 記録機能で勝負しない。手続き管理で選ばれる設計にする |
| 個人情報漏洩 | 高 | 要配慮個人情報として扱う。氏名・写真の端末内保持を検討 |
| App Store 審査 (医療系) | 中 | 監修者明記、医学的主張の根拠準備 |

## 15. 未決事項
